# Proposal: Unified Aporte Definition + Assignment + Cobro Generation (aporte-cobro-unificado)

## Intent

The archived `tipos-aporte-cobros` model (implemented and verified) is CORRECT about the definition schema — `aportes_definicion` with `monto`, `recurrencia`, `inicio`/`fin`, `modalidadPago`, `aplicaGrupoId`, `activo`; many-to-many `socio_aportes`; definition-driven generation with no override. What the user corrected (authoritative) is the **FLOW**: the current UI splits aportes into two disconnected steps — a definition form in the "Crear" tab AND a separate "Generar Cobros" section that manually selects definitions + socios + gestión to materialize records. This does NOT match the intended product behavior:

- **ONE SINGLE FORM.** Creating an aporte defines its fields AND assigns it to **socios** (multiselect), to a **group**, or to **nobody** (unassigned, to be assigned later from the socio form). No separate "define" and "generate" steps.
- **INTERNAL ID.** The aporte id is generated by the server (UUID). The user never chooses a slug (client-supplied `id` like `ap-mensual` disappears from the API contract; seeded slugs remain valid as stable internal ids for the default definitions).
- **AUTOMATIC GENERATION AT ASSIGNMENT.** Creating a definition and assigning it generates the cobro records right away (per `recurrencia` within the vigencia window). For a group: CURRENT members receive records at creation/assignment; FUTURE members receive them when they join the group (generation at membership time). Assigned "a nadie" → no records yet.
- **SOCIO FORM GENERATES TOO.** Saving a socio with aportes assigned generates that person's cobro records automatically.
- **MANDATORY DEDUP.** Never duplicate a record for the same (socio, aporte, mes, gestion) — across all generation paths.

The read-time group inheritance resolution (read-only `aportesInherited` chips) and the many-to-many schema are UNCHANGED; only the record-generation timing becomes event-driven (at assignment/membership) instead of "never pre-generated by membership alone". This is a behavior correction, not a schema rework.

## Scope

### In Scope
- **API — definition creation with embedded assignment** (`packages/api/src/routes/aportes-definicion.ts`): `POST /api/aportes-definicion` accepts `socioIds?: string[]` (direct assignment to socios, multiselect) alongside the existing fields (`aplicaGrupoId` keeps meaning "apply to group"); the `id` field in the body is IGNORED — the server always generates a UUID; the transaction inserts the definition + `socio_aportes` rows + GENERATES cobro records for the resolved target set (direct socios ∪ current members of the group when `aplicaGrupoId` is set) using the shared dedup generator, scoped to socios whose estado permits `aportes`. Response `201 { definiciones, generados: { count, items } }`.
- **API — auto-generation on socio create/replace** (`packages/api/src/routes/socios.ts`): `POST /api/socios` generates records for the assigned `aporteIds` AND for group-scoped definitions of the assigned groups (membership-time generation, decision d); `PUT /api/socios/:id` runs the dedup generator over the resulting assignment/membership set (idempotent — newly added definitions/memberships generate, re-saved ones are no-ops). Response reports the generated count. No record deletion when an assignment/membership is removed (cobros already generated are never deleted).
- **API — dedup invariant** (`packages/api/src/lib/aportes.ts`): the shared record generator gains dedup — inside the transaction, skip any (socio, aporte, mes, gestion) that already exists. Applies to the auto-generation paths AND the existing `POST /api/aportes`, `/bulk`, `/bulk/all` (which currently can duplicate on re-run). Optionally backed by a partial unique index on `aportes(socioId, aporteId, mes, gestion)` where `aporteId IS NOT NULL` (additive, design-phase decision, validated against existing data).
- **Store** (`apps/web/src/stores/app.store.ts`): `addAporte` passes `socioIds`/`aplicaGrupoId` and handles the new creation response; `createSocio`/`updateSocio` propagate the generated count and refresh `aporteRegistros` so cobros appear immediately.
- **UI — aportes.tsx** (`apps/web/src/routes/aportes.tsx`): the "Crear" tab becomes ONE unified form — definition fields (nombre, monto, recurrencia, inicio/fin, modalidadPago) + an "Asignar a" section (socios multiselect | group select | "no asignar ahora"). The standalone "Generar Cobros" section is REMOVED (its logic is absorbed by the assignment step of the unified form). No `id` input (server-generated; shown read-only when editing). Definition list/edit/delete and the "Pagar" tab stay.
- **UI — socios.tsx** (`apps/web/src/routes/socios.tsx`): aporte multiselect already exists; saving a socio with aportes/memberships triggers generation server-side and the UI shows the generated count (toast) + refreshes the cobro list.
- **Tests** (`packages/api/test/`): update `aporte-definicion.test.ts`, `socios-aportes.test.ts`, `aportes-generacion.test.ts`, `aportes-bulk-all-pagos.test.ts` for the new POST semantics, server-generated id, and response shape; NEW coverage for the dedup invariant, membership-time group generation, "a nadie" creation (no records), and socio-save generation.
- **Specs deltas** (spec phase): modify `openspec/specs/aporte-definitions`, `openspec/specs/payments`, `openspec/specs/socios-estados` (see Dependencies).

### Out of Scope
- **Definition schema**: `aportes_definicion` fields, `socio_aportes` many-to-many join, seed slugs (`ap-mensual` etc.) — unchanged.
- **Read-time group inheritance**: `aportesInherited` read-only chips resolved dynamically from membership — unchanged (this is the "herencia por grupo dinámica" that stays).
- **`GET /api/aportes/:id/pagos`**, payment/anulación flows (`/:id/pagar`, `/:id/anular`), enforcement por estado via `cargarPermisosPorEstado`/`permite`, partial payments — unchanged.
- **Retroactive generation**: existing definitions/socios are NOT retroactively regenerated; generation applies to assignments made after this change. (Migrating pre-existing assignments into records is deferred — flag if needed.)
- **Reports/dashboard/egresos/notifications/export** — untouched.
- **Bulk endpoints removal**: `POST /api/aportes`, `/bulk`, `/bulk/all` are RETAINED at API level (tests and catch-up generation may still use them; now dedup-safe). Only their UI entry point (the "Generar Cobros" section) is removed. Defer removal decision to the user.

## Product Decisions Taken (user, authoritative)

- **(a) One single form.** In the Aportes section (Crear tab), creating an aporte defines its fields AND assigns it to socios (multiselect), to a group, or to nobody — there are no two separate steps ("definir aporte" + "generar cobros").
- **(b) Internal server-generated id.** The aporte id is a server-generated UUID; the user never supplies a slug. Seeded slugs remain as stable internal ids of the default definitions; the form does not ask for an id.
- **(c) Generation at assignment.** Creating an aporte and assigning it generates the cobro records for those socios immediately, per the definition's `recurrencia` and `inicio`/`fin` window. For groups: current members receive records at assignment; "a nadie" generates nothing yet.
- **(d) Future members inherit at membership time.** A socio added to a group that has a group-scoped definition receives its cobro records at the moment the membership is created (generation at membership), not by any later manual step.
- **(e) Socio form generates.** Saving a socio (create/replace) with aporte assignments generates that person's cobro records automatically; new assignments added on edit generate only the missing records.
- **(f) Mandatory dedup.** The system MUST never create duplicate records for the same (socio, aporte, mes, gestion) on any path (creation-with-assignment, socio save, membership change, bulk regeneration).

## Approach

1. **Core types** (`packages/core/src/index.ts`): `AporteInput` DROPS the optional `id` (server-only); POST definition input gains `socioIds?: string[]`; reuse `AporteBulkResult`-shaped `{ count, items }` for the `generados` part of the creation response; socio request/response types unchanged.
2. **Shared dedup generator** (`packages/api/src/lib/aportes.ts`): extend the existing `generarAportes` (used by single/bulk/bulk-all) to skip inserts where a row for (socioId, aporteId, mes, gestion) already exists inside the transaction (SELECT-before-INSERT or `insert ... onConflictDoNothing` against the partial unique index if adopted). Add a helper `definicionesDeGrupos(grupoIds)` to resolve group-scoped definitions for membership-time generation. `mesesParaDefinicion`/`mesesDefinicion`/`socioHoldsAporte` are reused as-is.
3. **POST /api/aportes-definicion** (`routes/aportes-definicion.ts`): body `{ nombre, monto, recurrencia, inicio, fin, modalidadPago, aplicaGrupoId, activo, socioIds? }`; `id` in body ignored → `crypto.randomUUID()`; transaction = insert definition → insert `socio_aportes` rows for `socioIds` → resolve target set (direct socios ∪ current members of `aplicaGrupoId`'s group, primary + additional) → dedup-generate records for socios whose estado permits `aportes` (bulk-exclusion pattern), `gestion` = current year by default (no `mes` override at creation). Response `201 { definiciones, generados }`. `PUT`/`DELETE` unchanged (field edit only; assignments/generation happen at creation or via the socio form).
4. **Socio create/replace** (`routes/socios.ts`): in the SAME transaction that inserts/replaces `socio_aportes` and `socio_grupos`, run the dedup generator over (a) the final `aporteIds` set and (b) the group-scoped definitions of the final membership set (primario + adicionales) — new memberships generate, re-saves are no-ops, removals never delete records. Enforcement: a socio whose estado does not permit `aportes` keeps its assignment but generates 0 records (consistent with bulk exclusion; the socio save itself does NOT 409). Response includes `generados: { count }` (exact shape per design).
5. **grupos.ts**: NO change — there is no standalone group-membership endpoint; membership mutations flow through socio POST/PUT, so the "generation at membership" hook lives in `routes/socios.ts`.
6. **Store** (`apps/web/src/stores/app.store.ts`): `addAporte` sends `socioIds`/`aplicaGrupoId` and stores the returned `definiciones` + surfaces `generados.count`; `createSocio`/`updateSocio` refresh `aporteRegistros` after save (and return/record the generated count for the toast).
7. **UI aportes.tsx** (`apps/web/src/routes/aportes.tsx`): the Crear tab's two cards (definition form + "Generar Cobros") merge into ONE form: definition fields + "Asignar a" section with three modes — socios multiselect (only socios with `aportes` permission, reusing the existing `permitidos` filter), "o a grupo" (single group select → sets `aplicaGrupoId`), "o a nadie" (default). Live hint of how many cobros will be generated for the current gestión (computed from `recurrencia` ∩ window) before submit. After submit: toast with the generated count, close modal, refresh the cobro list. The definition list (edit/delete with the existing 409 guard) and the "Pagar" tab are untouched.
8. **UI socios.tsx** (`apps/web/src/routes/socios.tsx`): multiselect stays; on save show a toast "Se generaron N cobro(s)" (from the response) and the cobro list refreshes so the new records are visible immediately.
9. **Tests** (`packages/api/test/`): rework the POST-definition scenarios (server-generated id, `socioIds` assignment, response shape); add: dedup invariant (same socio+aporte+mes+gestion never duplicated across create-with-assignment, socio re-save, and bulk re-run), membership-time generation (socio joins group with scoped definition → records appear; joining again → no duplicates), "a nadie" creation → 0 records, unassigned definition later assigned via socio form → records generated, non-permitted socio → assignment kept, 0 records.
10. **Specs deltas** (spec phase): `aporte-definitions` (MODIFIED: POST semantics with `socioIds` + generation, id server-generated, group application now pre-generates for current members at assignment, future members generate at membership — the "MUST NOT pre-generate" clauses are inverted); `payments` (MODIFIED: auto-generation at assignment/membership as a new trigger + dedup invariant across single/bulk/bulk-all/auto); `socios-estados` (MODIFIED: membership SHALL generate records — replacing "NO record by membership alone" — and socio save generation + dedup).

## Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Archived behavior "no pre-generated records by membership alone" is inverted — consumers (tests, reports, chips) assume dynamic-only resolution | Med | Update ALL three specs in the same change; keep read-time `aportesInherited` chips unchanged; verify phase re-checks every archived scenario that asserted "NO record by membership" |
| Double-generation across paths (definition+socioIds, socio re-save, bulk re-run) creates duplicates | Med | Dedup in the shared generator (single code path for every trigger) + optional partial unique index; dedicated tests prove idempotency |
| `POST /api/aportes-definicion` response shape change (`{ definiciones, generados }`) breaks the store/UI and existing tests | Med | Store and UI updated in the same change; tests reworked together; keep the full definitions list in the response so the catalog remains derivable |
| Auto-generation uses the current gestión; a definition whose window doesn't intersect it silently generates 0 records | Med | Live "cobros to generate" hint in the form before submit; treat 0-record generation as valid (existing window-expired behavior); confirm default gestión at spec phase |
| Non-permitted socio in `socioIds` gets an assignment but 0 records (silent) | Low | UI already filters the multiselect to permitted socios; document the skip semantics in the spec; bulk-exclusion pattern reused |
| Socio PUT becomes heavier (generation side effects in a transaction) | Low | Generation only for the final assignment/membership set with dedup; records are small; same transactional pattern as existing bulk |
| Seeded slugs vs server UUIDs: code assuming slug format (e.g. deriving defaults from `ap-mensual`) breaks | Low | `aporteDefActivoDefault` uses rowid-first-active, not the slug; audit for slug-based assumptions in the change |

## Rollback Plan

- **Non-destructive**: this change makes NO schema drops; the only optional schema item is an additive partial unique index (droppable at will).
- **Code**: revert routes/store/UI via git; the archived `tipos-aporte-cobros` behavior is recoverable by restoring the previous `POST /api/aportes-definicion` and the "Generar Cobros" UI.
- **Generated records**: cobro records created by the new auto-generation are identifiable (`aporteId` = UUIDs created after this change, `gestion` = target year). If the change is reverted, a one-off cleanup can delete them (they have no payments in the window of the change); normal flows NEVER delete records, so nothing else is disturbed.
- **Dedup guarantee**: app-level dedup is code; if the partial unique index is added and must be removed, it is a single additive-migration revert.

## Success Criteria

- [ ] Creating an aporte in the single form assigns it to socios (multiselect) / a group / nobody, generates cobros immediately (per `recurrencia` ∩ window), and the cobro list updates without a manual step
- [ ] The `id` field is never accepted from the client (POST ignores it); the server generates a UUID; seeded slugs (`ap-mensual`) remain working as internal ids
- [ ] Adding a socio to a group with a scoped definition generates that socio's cobros at membership time; a group-assigned definition generates cobros for current members at creation
- [ ] Saving a socio with aporte assignments generates that person's cobros; editing to add aportes generates only the missing records
- [ ] Dedup: no duplicate (socio, aporte, mes, gestion) exists after any combination of creation-with-assignment, socio re-save, and bulk regeneration
- [ ] The standalone "Generar Cobros" section is gone from the Crear tab; the tab exposes one unified form
- [ ] Assigning "a nadie" creates no records; the definition can be assigned later from the socio form
- [ ] `pnpm typecheck` passes and build compiles; UI usable at ~360px
- [ ] Specs updated: `aporte-definitions`, `payments`, `socios-estados` reflect the unified flow, server id, and dedup invariant
